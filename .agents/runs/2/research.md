# Studio Miraie：カフェ向け無料診断フロー調査

調査日：2026-11-08。Web検索と公開ページ・一次資料の本文確認を実施した。事例の申込・送信や実機での診断完走は行っていない。以下は「確認できた知見」「提供者の公開事例」「Studio Miraieへの設計提案」を区別する。提案中の質問数・表示件数・寸法は設計値であり、効果の統計ではない。価格と募集枠はユーザー提供条件を出典とする。

### 質問数と順番

最適な質問数を一律に決める根拠は確認できない。「短いほど必ず良い」「一定数なら完了する」とは言わない。必要な改善提案に使わない質問を削ることを優先する。GOV.UKの質問設計指針も参照する。[出典](https://www.gov.uk/service-manual/design/form-structure)

本案は最大7問（ユーザー指定の上限）。店名・住所・売上・URLなどの入力は診断に不要とする。店主が把握しやすい現状から入り、同じ媒体に関する問いを近くに置く。ホームページがなければ、その見やすさを尋ねない。「わからない」を用意し、調べ直すための外部移動を要求しない。連絡先は結果表示後の相談導線に分離する。これらの並び順・連絡先配置は今回の提案であり、各項目の改善率データはない。

## 3. 具体案：カフェ店主向け診断フロー

### 入口の文案

**「お店のWeb案内、どこから整える？ 無料セルフチェック」**

「最大7問、選ぶだけ。回答をもとに、今できる改善を整理します。結果を見るための名前・メールアドレスは不要です。サイトやGoogleマップを自動検査するものではありません。」

ボタン：「無料でチェックする」。時間は未計測のため初版では省略する。

### 質問文と選択肢

すべて単一選択。括弧内は内部コードで、利用者には表示しない。選択肢は評価語ではなく観察できる状態にする。

| 問 | 質問文 | 選択肢 |
| --- | --- | --- |
| Q1 | お店のホームページはありますか？ | お店のホームページがある（site）／Instagramや店舗紹介ページだけを使っている（social）／どちらも使っていない（none）／わからない（unknown） |
| Q2 | ホームページのメニューや営業時間は、スマホで拡大せずに読めますか？ | 読める（yes）／拡大が必要・読みにくい箇所がある（issue）／まだ確認していない（unknown） |
| Q3 | 営業時間やメニューが変わったとき、主な案内先を更新できていますか？ | 自分やスタッフですぐ更新できる（ready）／依頼先に頼めば更新できる（delegate）／更新に困る・古い情報が残る（issue）／案内先がない・わからない（unknown） |
| Q4 | Googleマップのお店情報は、現在の営業内容と合っていますか？ | 住所・営業時間・連絡先を確認し、合っている（yes）／古い情報や不足がある（issue）／お店が表示されていない（absent）／確認していない・わからない（unknown） |
| Q5 | Instagramから、営業時間・場所・メニューの案内へ迷わず進めますか？ | プロフィールのリンクなどから進める（yes）／投稿を探さないとわからない・案内が不足（issue）／Instagramは使っていない（unused）／わからない（unknown） |
| Q6 | 来店前に連絡したいお客様へ、連絡方法をわかりやすく案内していますか？ | 電話・問い合わせ・予約先などを案内している（yes）／案内しているが探しにくい・使いにくい（issue）／連絡を受けたいが案内先がない（absent）／事前連絡を受け付けていない（notneeded）／わからない（unknown） |
| Q7 | 今のお店の雰囲気やメニューが伝わる写真を、Web上に載せていますか？ | 今の外観・店内・主なメニューが伝わる（yes）／暗い・古い・一部しか伝わらない（issue）／写真を載せていない（absent）／わからない（unknown） |

Q2はQ1=siteのときだけ出す。他は省略し、残りの問いは全員に出す。画面上の問番号は表示順で振り直し、内部IDは変えない。Q1に戻って回答を変更した場合、不要になったQ2の回答は破棄し、結果に残さない。Q1=unknownでQ2を省略しても「スマホ対応に問題あり」とは判定しない。

Q3の補足：「主な案内先とは、ホームページ・Instagram・Googleマップなど、お客様に見てほしい場所です。」Q6の補足：「予約を受け付けていないお店でも、必要な問い合わせ方法があれば構いません。」Instagramの利用やオンライン予約を全店の必須条件にしない。

### 画面遷移

入口 → 質問（選択→次へ、戻る可） → 最終問の「結果を見る」 → 結果全文 → 任意の無料相談／パッケージ詳細。

質問中に連絡先入力や営業ページを挟まない。結果から「回答を見直す」で回答済み一覧へ戻れ、各問を修正して再計算できる。「最初からやり直す」は別に設ける。所要時間を演出するための偽の分析待ち画面は不要。

### 結果画面：総合スコアは表示しない

自己申告だけで「集客力」「SEOの強さ」を数値化する根拠がないため、点数・偏差値・同業店順位・売上損失額を出さない。見出しは「お店のWeb案内：見直しポイント」。回答内容に応じて以下を表示する。

1. 冒頭に「これは回答に基づくセルフチェックです。サイトの実測・検索順位の確認・専門家による個別調査は行っていません」。
2. 「回答上、整っていること」。yes・readyに対応する具体的内容を列挙。delegateは「更新の依頼先あり」とし、遅い・悪いと決めつけない。
3. 「まず見直すこと」。各カードを「あなたの回答 → 確認する理由 → 自分でできる行動」の順で記載。
4. 「まだ確認していないこと」。unknownを問題と分け、確認手順を出す。
5. 回答と全改善項目を開ける一覧、結果のコピー・印刷、回答の見直し。
6. 無料相談CTAと、任意のモニター詳細導線。

表示優先ルールは運営上の編集方針として公開し、効果予測とは呼ばない。明確な不備は、来店前の基本情報（Q3・Q4）→読めること・連絡できること（Q2・Q6）→媒体間の案内・写真（Q5・Q7）の順に提示する。最初の表示は最大3件、残りも一覧で隠さず確認できる。Q1でホームページなしの場合は、まず既存媒体に基本案内を揃える提案を返し、制作を唯一の解決策にしない。

unknownだけなら「まず現状を確認しましょう」とし、不備を確定しない。notneeded・unusedは減点も警告もしない。すべて整っていれば「今回の回答では、優先して直す項目は見つかりませんでした」。無理に制作相談へ誘導しない。

結果カード例：

> **Googleマップの営業時間を確認しましょう**  
> あなたの回答：「古い情報や不足がある」  
> 来店前に確認する情報と実際の営業内容を揃えるため、まず通常営業時間と臨時休業の案内を確認してください。ホームページやInstagramの案内も見比べましょう。

「このままだと客を逃す」「改善すれば順位が上がる」「他店より劣る」など未確認の断定はしない。Googleはローカル検索が関連性・距離・知名度などで決まると説明しており、情報整備だけから順位や売上を保証できない。[Google公式ヘルプ](https://support.google.com/business/answer/7091?hl=ja)

### 結果から相談・モニター募集へのCTA

主CTA：「この結果について無料で相談する」  
補足：「自分で直すところと、制作を頼むとよさそうなところを一緒に整理します。」無料相談の時間や対応範囲は運営側が確定した内容だけ表示する。

副CTA：「カフェ向けホームページ制作の内容を見る」。主CTAと同じ強さのボタンを並べず、結果を読んだ後に提示する。

モニター案内文のたたき台：「制作を検討している方へ。通常148,000円／モニター98,000円・先着3店。対象・協力条件・制作範囲をご確認ください。」価格・募集枠の出典は本依頼のユーザー提供情報。税込／税別や追加料金は未提示のため断定せず、公開前に販売ページと整合させる。残枠は実際の受付状況に合わせて手動更新し、募集終了後は削除または終了表示。根拠のない残数・期限・成果事例を出さない。

相談への移動時に「結果をコピー」を提供する。店名・返信先・相談内容は相談先で初めて入力する。診断を済ませたから連絡先入力も必須、という扱いにはしない。

## 4. 実装メモ：静的HTML＋JavaScript

- 診断は単一HTML内の画面切り替えで実現可能。質問定義・回答コード・改善文・優先順をJSのデータとして持ち、純粋関数 `evaluate(answers)` で結果を生成する。外部AI・API・URL巡回は不要。自己申告診断と明記し、自動解析と誤認させない。
- 状態は `version / currentQuestionId / answers` を基本とする。各問の選択を状態へ保存し、表示対象質問をQ1から再計算する。通常はメモリ、再読み込み対策が必要なら `sessionStorage` を併用。保存失敗でも診断を継続し、ブラウザを閉じた後の再開は約束しない。保存するのは回答コードのみ。リセットで消去する。
- `fieldset`・`legend`・ネイティブradio・`label`・実際の`button`を使う。非表示画面は`hidden`にし、次の画面の見出しにフォーカスを移す。未選択で次へを押したら「選択肢を選んでください。わからない場合も選べます」とその場で通知。フォーカス可視化、キーボード操作、色以外の選択表示を用意する。
- バーに加えて進捗を文字で表示。画面内の戻るとブラウザの戻るを整合させるため、状態遷移にHistory APIを利用し`popstate`で復元する。回答データ自体はURLに入れない。入口より前へ戻る操作を捕捉して離脱を妨げない。
- モバイルの設計値としてタップ領域の高さを最低44 CSS px、本文を16 CSS px以上を目安にする（本案の設計値。完了率の統計ではない）。拡大を禁止せず、横スクロールや固定要素による覆いを防ぐ。動きを減らす設定に対応する。内部UIスキルは進捗・フォームのフィードバック・固定要素による遮蔽防止の補助として参照した。外部の効果根拠には用いていない。
- 結果は`textContent`などで安全に描画。コピーはClipboard API失敗時に選択可能なテキストを表示。印刷用CSSで結果と回答を出し、ブラウザの印刷／PDF保存に対応する。JS無効時は診断にJSが必要な旨と既存の相談リンクを表示する。
- バックエンドなしでは相談内容の受信・メール送信・予約管理はできない。既存の稼働する相談窓口へ通常のリンクを張る。既存窓口がメールだけなら`mailto:`とコピー可能なアドレスを出すが、メールアプリが必要な点を補足する。「送信しました」をクリックだけで表示しない。外部フォームを使う場合は外部サービス利用であり、別途個人情報の取扱いと稼働確認が必要。
- 「回答は送信されません」と表示できるのは、解析や外部送信も含め実装を確認した場合だけ。アクセス解析があるなら診断回答の扱いとページ閲覧計測を区別して説明する。

### 公開前の確認と改善の測り方

確認対象は、Q1によるQ2の分岐、Q1変更時の回答消去、全unknown・全良好・全不備、予約不要／Instagram未使用、戻る・再読み込み・保存不可、スマホ・キーボード・読み上げ、結果コピー、相談リンクの到達。結果文が選択内容と矛盾しないことを確認する。

診断開始を`start`、設問表示を`question_view`、結果表示を`result_view`、相談リンクを`consult_click`として区別すると、停止位置を調べやすい。解析導入時だけ外部へ送信し、氏名・連絡先・自由入力・回答本文をイベントに含めない。同一診断内での戻り・再描画は重複集計しない。

- 開始者完了率＝結果到達した診断セッション数 ÷ 開始した診断セッション数。
- 設問からの未到達率＝その設問を見たうち結果到達しなかった診断セッション数 ÷ その設問を見た診断セッション数。ブラウザ終了を即時の確定離脱とせず、集計期間を明示する。
- 相談クリック率＝相談リンクを押した診断セッション数 ÷ 結果到達した診断セッション数。クリックは相談申込・成約ではない。

外部解析もサーバーログ集計も使わなければ、利用者全体の完了率は把握できない。まず対象の店主に操作してもらい、迷う言葉や読みにくさを修正する。将来比較するなら、質問・結果・連絡先条件・流入を揃えてステップ版と1ページ版を比較し、開始率と開始後の完了率を分ける。少数のアクセスによる上下だけで優劣を断定せず、母数と期間を併記する。

## 5. 採用判断

最大7問の選択式ステップ診断を採用する。連絡先不要で改善案まで渡し、点数の代わりに「整っていること・見直すこと・未確認」を返す。無料相談は結果の理解を助ける導線、モニター募集は希望者が制作条件を確認する導線とする。離脱削減の効果は公開後に検証し、順位保証や架空の実績で補わない。
